# Notebook design

How the analysis notebooks are laid out, and why. The notebooks are generated by
`tools/make_notebook.py`, so this document is the specification that generator implements.

The layout is shared by every track in [scope-map.md](scope-map.md). The worked examples
below use Track B (infection inside one host). Other tracks keep the same sections and swap
in their own glossary, baseline and known-answer test.

## Two readers, one file

| | Wet-lab reader | Computational reader |
|---|---|---|
| Wants to know | What does my data say? What should I run next? | Is this correct? Can I reproduce it? |
| Reads | Markdown, figures, the status panel | Code, parameter tables, diagnostics |
| Opens | The rendered HTML report | The `.ipynb` or the package source |

Both read the same file. Code cells carry the tag `hide-input`, so the rendered HTML report
(Quarto or Jupyter Book) folds them by default and either reader can expand them. Logic lives
in the package; a code cell is at most a few lines that call it and display the result.

## Conventions used in every notebook

**Status lines.** Each analysis section ends with one line per check:

```
PASS  6 subjects, every subject has >= 4 time points
WARN  31% of observations below LOD (1.0 log10 TCID50/mL); censored likelihood in use
FAIL  units missing for column 'titer'; stopping
```

A `FAIL` raises an exception and stops the notebook. Nothing downstream runs on data that
failed validation. The final section collects every status line into one panel.

**Bench translation.** Every model parameter appears once in a glossary table with four
columns: symbol and unit, what it means biologically, how you would measure it at the bench,
and whether this dataset constrains it.

| Symbol | Unit | Biology | Bench measurement | Constrained here? |
|---|---|---|---|---|
| β | mL / (virion · day) | How readily a virion infects a target cell | Hard to measure directly | Only jointly with p |
| δ | 1/day | Death rate of infected cells | Infected-cell half-life, ln 2 / δ | Yes |
| p | virions / (cell · day) | Virions released per infected cell per day | Single-cycle yield assay | Only jointly with β |
| c | 1/day | Clearance of free virus | Virion decay in medium or wash | Partly; correlates with δ |

The "constrained here?" column is filled from the identifiability section, not typed in by
hand. The example rows above show the format only.

**Predict, then reveal.** Before each simulation, a markdown cell asks the reader to commit
to a guess, for example "If clearance c doubles, does peak viral load halve, fall less, or
fall more?". The answer appears in the cell after the plot. This comes from the teaching
design of DSAIRM.

**Baseline beside every fit.** No mechanistic fit is shown alone. The no-information
comparison is a log-linear model (exponential growth then decay, no mechanism). If the
mechanistic model does not beat it on held-out points, the notebook says so in the status
panel.

## Per-dataset notebook (01–03): section by section

### 0. Question card

Markdown only. Five lines:
- The biological question
- The system (virus, host, in vivo or in vitro)
- The assay and its unit, plus the LOD
- What a positive result would look like
- What this notebook cannot tell you

### 1. Your data

- Fetch through the cached, checksummed layer. Print the source URL, access date and
  checksum.
- Show the dataset metadata as a table: assay, unit, LOD, number of subjects, number of
  observations, infection-time status (known / unknown).
- Plot every subject's raw trajectory, with points below LOD drawn as open markers at the LOD
  and labelled as censored.
- Status lines: units present, LOD read from source, minimum time points per subject,
  fraction censored.

### 2. The model in pictures

- Flow diagram of the model compartments, generated from the model definition so it
  cannot drift from the code.
- The equations, once, in LaTeX.
- The bench translation glossary.

### 3. Explore before fitting

- Predict-then-reveal question.
- Simulation with the literature parameter values, overlaid on the data.
- Interactive version (sliders) only in the live notebook; the HTML report shows a fixed
  small-multiples grid of the same parameter sweep, so nothing depends on a running kernel.

### 4. Can the data pin the parameters down?

- Structural identifiability: the result for this model and observable, with the tool and
  version that produced it.
- Practical identifiability: profile likelihood for each parameter. Plot each profile
  against the 95% threshold.
- Parameters with a flat or one-sided profile are marked unidentifiable and either fixed (with
  the source of the fixed value stated) or reported as a combination.
- Status lines: one per parameter.

### 5. Fit

- Censored likelihood: points below LOD contribute P(y < LOD), not a density at LOD/2.
- Side-by-side: the same fit with LOD/2 substitution, to show the size of the bias on this
  dataset. This is a teaching comparison and the substituted fit is never reported as a result.
- Baseline fit (log-linear) and the mechanistic fit on the same axes.
- Parameter table: estimate, 95% interval, unit, fitted or fixed, and the source of any fixed
  value. Goodness-of-fit sits next to the count of fitted parameters.
- Posterior or residual predictive check plotted per subject.

### 6. Known-answer checks

- Synthetic data generated from known parameters, with this dataset's sampling times, noise
  level and LOD. The fit must recover the known values within their intervals. This is the
  positive control: it shows how much this sampling design can resolve at all.
- Agreement with the reference implementation, DSAIRM in R, for the same parameters, within a
  stated tolerance.

### 7. Sensitivity

- How the conclusion changes with the LOD treatment, the prior (Bayesian fits), and the
  fixed parameters' values. Shown as a scan, not a single alternative.

### 8. What this means at the bench

Markdown, written for the wet-lab reader:
- Three to five plain-language takeaways, each pointing to the figure that supports it.
- What the data could not resolve, and the cheapest extra measurement that would resolve it
  (taken from section 4 and notebook 05).

### 9. Status panel and provenance

- Every status line from sections 1–7 in one table.
- Provenance: package version, environment file hash, Python and library versions, seed,
  hardware, run date, wall time.

## Notebook 05: design your experiment

The notebook a wet-lab researcher opens before running an experiment.

**Input.** A small CSV describing the plan: sampling times, subjects per group, assay, LOD,
expected noise. Alternatively, pick one of notebooks 01–03 as the reference system.

**What it does.**
1. Simulates the planned experiment many times from the fitted model, with assay noise and
   censoring at the LOD.
2. Refits each simulated dataset.
3. Reports, for each parameter, the interval width you can expect and whether it would be
   identifiable.
4. Compares the plan against a few alternatives (an extra early time point, more subjects,
   a more sensitive assay) and ranks them by how much they narrow the key interval.

**Output.** One table and one figure: "with this plan you can expect to estimate the
infected-cell half-life to within ±X hours; adding a sample at day 1 narrows that to ±Y". The
smallest effect the planned design could detect is stated explicitly.

## Per-system config

One config per system; the analysis code is identical across systems. Anything a system needs
handled specially is named in its config, following the SAXS repository's `System` pattern.

```python
@dataclass
class System:
    index: str                    # notebook number prefix, e.g. "01"
    slug: str                     # file name stem
    name: str                     # full name, for prose
    source_url: str               # where the raw data comes from
    sha256: str                   # checksum of the raw file
    license: str                  # as stated by the source
    assay: str                    # e.g. "RT-qPCR Ct", "TCID50"
    observable_unit: str          # read from source, never inferred
    lod: float                    # in observable_unit, read from source
    infection_time_known: bool
    model: str                    # key into the model catalogue
    fixed_parameters: dict        # name -> (value, unit, source)
    question: str                 # question-card text
    why_this_system: str          # opening framing
    caveats: list[str]            # system-specific traps, named, not worked around
    seed: int = 20261013
```

## Rendering

- The `.ipynb` is generated, executed and rendered to HTML. Outputs are stripped before commit
  (`nbstripout`); the HTML report is the deliverable for wet-lab readers.
- Figures are saved as SVG plus a PNG preview and use a colorblind-safe palette (Okabe-Ito
  for subjects, viridis for continuous scales). Censored points always use open markers.
- Interactive widgets are optional extras in the live notebook. The report must stand alone
  without them.
